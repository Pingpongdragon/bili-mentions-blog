SKILL.state：长程 Agent 只带“下一步需要的状态”

UP：Agent智能体深度研究院 · BV1cVtn6AEZ3 · 2026-11-21

一句话总结SKILL.state 用技能说明+结构化状态+最新观察驱动每步，模型提状态补丁与动作，程序校验后丢弃推理；200 步仓库任务 token 617万→12万，分数 0.84→0.94；抗噪强，但依赖预设 schema。

一句话总结

论文 SKILL.state 提出：长程 Agent 不必把每一步的观察、动作、推理都追加进上下文，而是只保留技能说明 + 当前结构化状态 + 最新观察；模型每步输出“状态补丁 + 动作”，程序校验后再执行，并丢弃本步推理。200 步仓库任务里，token 从 617 万降到 12 万，分数从 0.84 升到 0.94。

视频讲了什么

先讲问题：Agent 每做一步都把观察、动作、推理接进下一轮，任务越长，旧动作、过时工具输出和无关观察越多；每一轮重复处理这些内容，成本接近二次增长，还会干扰模型对“当前事实”的判断。

SKILL.state 把每步输入拆成三部分：P（不可变的技能说明）、Σ（当前结构化执行状态）、O（刚拿到的最新观察）。模型只看这三样，输出本步动作和“状态补丁”；运行时做确定性校验——字段是否存在、类型和格式对不对——通过后合并成下一状态，再执行动作；本步中间推理在校验后丢弃，不再进入下一次提示词。

状态不是自由摘要，而是按领域预先定义的 schema。以 InterCode CTF 为例，只有五类字段：已发现的 flag、已测试的假设、当前活动文件、工作目录、命令摘要。空值可以表示删除字段；动作执行后，下一轮重新读取最新观察。这样历史推理不再承担主要信息载体，结构化状态才是。

实验分受控环境和公开任务。Warehouse 100 步：带滚动对话的状态型基线用 106 万 token，SKILL.state 用 6.5 万，分数 0.91→0.94；200 步：617 万 vs 12.2 万，分数 0.84→0.94。加入 50 个无关事件后，历史追加基线从 0.68 掉到 0.53，SKILL.state 仍为 0.98。公开任务 InterCode CTF pass@1 54.2%，τ-Bench Retail 58.3%、Airline 32.4%。

关键对照是“预算匹配”：输入都压到约 1800–1905 token 时，完整 ReAct 0.84、滑动截断 0.18、摘要封顶 0.52、LLMLingua 压缩 0.22，SKILL.state 0.94。作者想说明：效果不是因为“字少了”，而是状态字段能否准确承载下一步所需事实。

限制也讲得清楚：状态 schema 要提前设计；早期观察如果很晚才重新重要，丢了历史就找不回；审计、调试、解释过去动作时，历史轨迹本身就是目标；多 Agent 并发写状态还需要确定性冲突处理。小模型的主要错误不是不会推理，而是过早覆盖/删除状态、schema 理解与 JSON 格式。

关键点

  • 三件套输入：技能说明 P + 结构化状态 Σ + 最新观察 O。
  • 状态补丁：模型提动作和字段更新，程序校验类型/格式后再合并。
  • 丢弃推理：本步推理只进审计记录，不再占据下一次上下文。
  • 成本：200 步 617 万→12.2 万 token，分数 0.84→0.94。
  • 抗噪：50 个无关事件后仍 0.98，干扰在补丁阶段被过滤。
  • 不是“压短”：预算匹配下，截断/摘要/压缩都明显低于结构化状态。
  • 代价：依赖预先设计的 schema，漏写关键事实无法从历史恢复。
