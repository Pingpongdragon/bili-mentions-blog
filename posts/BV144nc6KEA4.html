DeepSeek Harness [09]：需求、架构与插件生态

UP：绿导师原谅你了 · BV144nc6KEA4 · 2026-11-04

一句话总结150 行 agent demo 不能当产品；DSH 用 microkernel + append-only session + event bus 换插件生态，但消不掉 essential complexity。

一句话总结

这节用「150 行 agent demo 为什么不能当产品」作引子，讲透两件事：需求会杀死架构；DSH 用 microkernel + append-only session + event bus 把能力让给插件生态。但插件只能消除 accidental complexity，消除不了 essential complexity。

视频讲了什么

开场先说 git 已经不够用：有 agent 后一个学生就拥有公司级组织架构，你是 CTO，要协调大量并行任务，于是设想只读锁、写锁、重构锁。接着用 150 行 agent 做三维校园：能跑，但断网即终止、没有会话恢复，demo 的假设是网络稳定；这就是 essential complexity（来自需求），不是再堆几个插件能消掉的。

然后讲需求如何杀死架构：五十万行写完上线，老板一句改需求，交互假设全崩。架构的本质是受限与自由的取舍——约束划出边界让 sub agent 并行，太自由等于没有架构；LAMP 单机最优、十亿人处处瓶颈，MapReduce 用两函数限制换容错。DSH 的选择是 microkernel：Cordis 管服务解析与插件装卸，session 是只追加的事件日志、唯一事实来源，模型历史由事件派生，event bus 按领域分类，插件还能修改尚未落盘的 pre-step 事件。

后半段是演示与生态：扔掉 UI slots 的 TUI、PDF、VS Code 式侧边栏；creator mode 让 agent 运行时拆装插件，现场加了一个超大号用量显示；WPS/Excel bridge 只支持「锁对象、交给模型、把修改拿回来」三步就接进生态；动态 UI 让模型输出带 JS 的 HTML 卡片。代价是插件语义会冲突、hook 顺序会打架，所以 DSH 用 pre-commit、类型检查、文档配对、CI gate 这些验证器来兜底，而不是靠人逐条列「不要」。

关键点

  • demo 的假设：网络稳定、进程不崩、会话可恢复；一旦这些假设不成立，demo 就不是产品。
  • 需求会杀死架构：早期决策会跟着软件一辈子；MVP 要先验证最危险的假设，不是先调按钮样式。
  • 架构 = 用限制换协作：LAMP、MapReduce、DSH 的 microkernel 都是主动放弃一部分自由，换可并行、可容错、可扩展。
  • session 是唯一事实：只追加事件日志，模型历史、UI、工具状态都从事件派生，才能回放、恢复、审计。
  • 插件生态的边界：插件能消 accidental complexity，消不掉 essential complexity；语义冲突要靠验证器和规范，不是靠更多插件。

适合谁看

正在做 agent 产品、插件系统、IDE/终端工具的人；以及想理解「为什么架构不是画图，而是划边界」的开发者。最好先知道一点 DSH/Cordis、事件溯源和 LAMP/MapReduce，否则后半段会有点快。
