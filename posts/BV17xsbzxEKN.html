南京大学副教授蒋炎岩：Mosaic 操作系统模型和检查器

UP：西安数学张老师 · BV17xsbzxEKN · 2026-11-04

一句话总结用 50 行玩具 OS + 500 行模型检查器复现教科书并发/崩溃例子，再提出把 Linux 6.0 状态映射回简单模型的逆 refinement。

一句话总结

蒋炎岩把「一切皆状态机」从操作系统课上的玩具，推到 Linux 内核验证：先用 50 行玩具 OS + 500 行模型检查器复现教科书里的并发与崩溃一致性例子，再提出把复杂的 Linux 6.0 状态映射回 2.6/玩具模型上做轻量验证的逆 refinement 思路。

视频讲了什么

报告从操作系统课的一个不同视角开始：不从「进程、虚拟内存」这些抽象出发，而从程序出发——C 程序、汇编、硬件，本质上都是状态机；执行一条指令就是一次状态迁移。应用程序能执行一条特殊指令 syscall，把控制权交给操作系统；但「system call 一定要 trap 进内核」并不是逻辑必然，只是实现选择。既然一切是状态机，原则上就可以把状态图跑出来，做 model checking。

于是他做了一个很小的玩具 OS：50 行版本有 4 个系统调用，后来扩展到 500 行、9 个系统调用，包括进程/线程、choose（非确定性选择）、字符设备读写、块设备读写、以及随时 crash。并发用 Python generator/coroutine 实现：yield 保存上下文，调度器在多个协程之间随机选一个恢复，从而串行地模拟并发。这个模型能复现操作系统教科书里的例子：fork 后 printf 的 6 个 hello、管道后更多 hello、生产者消费者、TOCTOU、crash consistency；模型检查器还能在几秒内证明教科书里「所有可能情况」的枚举没有漏。

接着是「snowball hypothesis」：如果一个 bug 最终能被复现，几乎总能找到一句简短的自然语言描述；于是从字典里枚举短句，再由领域专家翻译成测试输入，理论上可以找到系统里所有可修复的 bug。模型仍然重要：人理解复杂系统时，会不自觉地把它 reduce 成一个简单模型，再一层层加上现代系统的差异（比如文件系统从线性目录到 B-tree index）。但模型和真实系统之间有 gap：Linux 从 2.4 到 2.6 引入 RCU 后越来越复杂，还是不是原来那个东西？

他给出两条路：形式化验证（证明实现与可执行模型等价，但人工成本高）和基于模型的测试（他选的路线）。最后是一个进行中的想法：把 Linux 6.0 的状态映射回 2.6、再映射回 9 个系统调用的玩具模型，做 abstraction mapping；在模型上枚举「低内存、高并发、调度器随机」等场景，再映射回真实内核，做轻量级验证。报告也穿插了航母、USB 短路导致 CPU 100%、以及用 AI 改写程序让符号执行覆盖率从 30% 到 60% 的例子。

关键点

  • Everything is a state machine：程序、汇编、硬件、OS 都是状态机；syscall 只是特殊的状态迁移，trap 不是必须。
  • 50 行玩具 OS + 500 行 model checker：9 个 syscall、crash、choose，足以复现教科书里的并发/崩溃一致性例子。
  • 协程模拟并发：yield 保存上下文，调度器随机恢复，串行执行也能探索并发交错。
  • Snowball hypothesis：bug 有简短描述；枚举短句 → 翻译成测试输入，是模型测试的底层假设。
  • 模型 ≠ 现实：模型是简化；关键是理解模型损失了什么，用反例驱动补模型。
  • 逆 refinement：把复杂内核状态映射回简单模型，在模型上做轻量验证，再映射回去。
